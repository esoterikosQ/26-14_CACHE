## 명시적으로 활성화하는 count 패처

이 별도 실험은 패치 경계를 대체한다. 가드 캐시가 아니며 출력 동일성을 보장하지 않는다.
캐시 재사용은 비활성화한다. 모델은 검증한 OSC BLT처럼 가상 다음 바이트 슬롯을 포함한
`patch_lengths` 직접 입력을 지원해야 한다. 이 패키지는 원래 모델을 import하지 않는다.
먼저 호환되는 PyTorch 환경에 `lmdb` 선택 의존성을 설치한다.

```python
import json
import torch
from phdq_blt_cache.blt_patcher import CountPatcherAdapter
from phdq_blt_cache.count_patcher import BoundaryRule, CountConfig
from phdq_blt_cache.lmdb_counts import LMDBCountTable

with open(fit_report_path) as stream:
   fitted = json.load(stream)
config = CountConfig(**fitted["count_config"])
rule = BoundaryRule(**fitted["selected_rule"])
model.eval()
with LMDBCountTable(background_path) as background:
   if background.config != config or background.metadata["source_report_sha256"] != fitted["background_report_sha256"]:
      raise ValueError("Fitted rule and background do not match")
   adapter = CountPatcherAdapter(config, rule, background)
   adapter.reset()
   with torch.inference_mode():
      lengths = adapter.patch_lengths(input_ids, max_patch_length=model.config.max_patch_length)
      output = model(input_ids=input_ids, patch_lengths=lengths, use_cache=False)
```

입력은 최소 두 ID로 이루어진 패딩 없는 단일 배치의 전체 바이트 ID 접두부이며,
자료형은 `torch.long`이다. 접두부가 늘어날 때마다 `patch_lengths`를 다시 호출한다.
고정된 길이 배열을 `model.generate`에 전달하지 않는다. 새 ID만 인과적 온라인
카운트를 갱신하며, 짧아지거나 내용이 바뀐 접두부는 상태를 다시 구축한다.
문서·청크 사이에는 명시적으로 초기화하고 배경 저장소는 열린 상태로 유지한다.
요청 사이에서 어댑터를 공유하지 않는다. CPU 조회와 입력의 장치→호스트 동기화도
이 경로의 비용에 포함된다.

재현 가능한 소규모 진단 명령은 `python -m scripts.smoke_blt_count_patcher`다.
필수 인자는 `--blt-project`, `--model-checkpoint`, `--conversion-report`,
`--fit-report`, `--background`와 새 `--output` JSON 경로다.
`OPENBLAS_NUM_THREADS=8`을 사용한다. 실행 조건은 CPU 여덟 스레드, BF16 OSC eager,
GPU0, 캐시 없음, 합성 입력 세 개, 모드·입력당 최대 새 ID 16개다.
소스 식별 정보와 새 순차 계산의 패치 길이를 검증한다. 양쪽 모드 모두 원래 모델과
신경망 패처 가중치를 계속 로드하므로 기존 패처 제거에 따른 메모리 절감은 측정하지 않는다.

2026-10-27 RTX 5090 기본 동작 검사는 완성된 10GB LMDB와 기존 F1 선택 임계값
0.375로 통과했다. [실험 근거](../evidence/english_blt_count_smoke_20261027.json)를
참고한다. 합성 입력 58바이트에서 바이트 가중 BPB는 원래 패처 2.2824, count 2.2935였다.
생성 시간 중앙값은 223ms와 173ms였다. 입력·모드당 관측은 한 번뿐이고 실행 순서는
고정됐으며 캐시는 준비된 상태였다. 이는 진단이지 별도 평가 집합의 품질이나 가속
주장이 아니다. 모든 출력은 유효한 UTF-8이었고 한 쌍의 출력이 달랐으며,
16-ID 상한 전에 EOS에 도달한 경우는 없었다. 전체 생성 종료, 긴 문맥 품질과 반복
타이밍은 미검증 상태다. 이전 A100 캐시 출력 동일성 근거와 합쳐 해석하지 않는다.

## 확장 검증

같은 실행기는 `--extended --repeats 3 --max-new-tokens 512`를 지원한다.
여기에 기존 검증 NPZ 캐시를 가리키는 `--validation-labels`와 적합 규칙이 사용한
정확한 보고서를 가리키는 `--label-report`를 전달한다. 보고서 해시, 캐시 계약과
원본 파일 해시를 검사한다. 처음 64개 검증 문서에서 길이별(512/1024/2048 ID)로
첫 청크 접두부 두 개를 고른다. 이미 사용한 검증 입력이며 미사용 평가 집합이 아니다.
길이 사이에는 접두부가 중복된다. 원문과 ID는 내보내지 않는다.

각 실제 입력으로 양쪽 모드를 먼저 준비 실행한다. 시간 측정은 세 번 반복하며 모드
순서를 교대하고 온라인 카운트를 초기화한다. 같은 모드 안에서는 BPB와 생성 ID가
정확히 같아야 한다. 입력별 p50/p95와 개별 시간을 기록하되 세 번의 반복으로 신뢰할
만한 꼬리 지연을 추정했다고 보지 않는다. 생성에는 원래 프로젝트의 `encode_prompt`로
만든 합성 프롬프트 두 개를 추가하고 자연 EOS를 유지하며 양쪽 모두
`logits_to_keep=1`을 사용한다. EOS 없이 상한에 도달하면
`completed_with_generation_limits`로 기록하며 EOS 검증 성공을 주장하지 않는다.
각 사례가 끝날 때마다 같은 디렉터리의 `.progress.json` 파일에 진행 상황을 저장한다.

[확장 검증 근거](../evidence/english_blt_count_extended_20261027.json)에는 같은
RTX 5090의 긴 접두부 사례 여섯 개와 생성 실행 30회가 기록돼 있다.

| 입력 ID 수 | 원래 BPB | count BPB | 원래 초기 처리 p50 | count 초기 처리 p50 |
| --- | --- | --- | --- | --- |
| 512 | 0.830687 | 0.827806 | 17.5ms | 54.1ms |
| 1024 | 0.781391 | 0.780963 | 26.7ms | 124.1ms |
| 2048 | 0.762912 | 0.763028 | 68.9ms | 262.3ms |

BPB는 같은 길이 접두부 두 개의 평균이다. 초기 처리 p50은 해당 접두부의 관측 여섯 개를
합쳐 계산하며 CPU 조회·전송·손실 계산을 포함한다. count 초기 처리는 상당히 느렸다.
각각 512 ID를 생성한 모드별 15회 관측의 생성 중앙값은 원래 7.978초, count 6.334초였다.
프롬프트 다섯 개의 중앙값 범위는 각각 7.455-8.090초와 6.051-6.373초였다.
서로 다른 출력, 짧은 반복 입력, 준비된 상태와 단일 GPU라는 조건 때문에 일반화에는
한계가 있다. 출력 30개는 모두 유효한 UTF-8이었고 반복 실행의 ID와 BPB도 정확히 같았다.

**양쪽 모드 모두 각 15회 실행에서 EOS에 도달하지 않았다.** 기준 미충족이지 전체 생성
검증 통과가 아니다. 원래 모델도 상한에 도달했으므로 이것만으로 count 패처의 성능
퇴행을 입증할 수는 없다. 전체 생성 지원을 주장하기 전에 원래 체크포인트·프롬프트의
종료 동작을 조사하며, EOS를 강제하거나 예산을 몰래 늘리지 않는다. 긴 입력 사례의
최대 GPU 할당량은 약 9.38GiB, 프로세스 최대 호스트 RSS는 약 9.45GiB였다.
원래 패처 가중치는 계속 메모리에 상주했다.

## EOS 생성 예산 후속 검사

명시적으로 승인된 후속 검사에서 같은 프롬프트 다섯 개와 양쪽 모드에
`--repeats 1`을 사용하고 `--max-new-tokens`를 1024로 두 배 늘렸다.
[1024-ID 근거](../evidence/english_blt_count_eos1024_20261027.json)를 참고한다.
양쪽 모두 EOS에 도달하지 않았고(각 0/5), 실행 열 번 모두 1024-ID 상한에 도달했으며
유효한 UTF-8을 출력했다. 처음 생성한 512 ID는 이전 512-ID 실행과 정확히 같았다.
이전 실행은 상한 때문에 멈췄지만, 상한을 늘려도 자연 EOS 도달은 입증되지 않았다.
종료 검증은 여전히 미완료이며 예산을 더 바꾸기 전에 원래 체크포인트·프롬프트의
동작을 확인해야 한다. 이 단회 진단은 반복 성능 측정을 추가한 것이 아니다.

## 종료 동작 진단

[종료 진단 근거](../evidence/english_blt_termination_20261027.json)는 원래
`model.generate`와 기록된 수동 탐욕 생성 출력을 비교한다. 128-ID 접두부 다섯 개가
모두 정확히 일치했다. 실행 시 토크나이저·모델·생성 설정은 BOS1/EOS2/PAD3으로
일치했다. EOS2는 억제되지 않았으며 별도 생성 설정 파일이 없어도 실행 시 EOS 설정은
올바르게 적용됐다.

기록된 각 경로의 다섯 위치, 총 50회 관측에서 EOS는 허용 ID 중 한 번도 최상위가
아니었다. 원래 순위는 2-134, count는 2-137이었다. 최대 관측 EOS 확률은 각각
약 0.757%와 1.631%였다. 관측 가능한 다음 ID 예측 40개는 기록과 모두 일치했다.
모델은 계속 생성하거나 반복하는 쪽을 선호했다. 여기에는 수동 종료 루프의 버그나
count에만 있는 EOS 억제의 근거가 없다. 일부 출력은 문장 전체나 줄바꿈 바이트만 반복한다.

체크포인트는 `facebook/blt-1b`의 변환본이며 GEC 미세조정 체크포인트가 아니다.
GEC 구분자 프롬프트만으로 해당 작업이나 응답 끝 EOS 출력을 학습했다고 입증할 수 없다.
이전 GEC 프롬프트의 EOS 결과는 학습된 교정 시스템의 검증이 아니라 탐색 결과로 본다.
기반 모델의 임의 탐욕 생성이 자연스럽게 끝난다는 보장도 없다.
BPB·고정 길이 처리량과 작업 응답의 종료를 구분한다. 작업 종료에는 관련 입력과
EOS 목표로 학습했고 별도로 식별된 체크포인트가 필요하다. 실험을 통과시키기 위해
체크포인트를 몰래 바꾸거나 EOS를 강제하거나 반복 페널티를 추가하지 않는다.

진단 실행기 `python -m scripts.diagnose_blt_termination`는 `--blt-project`,
`--conversion-report`, `--background`, `--source-report`(1024-ID 결과)와 새
`--output`을 받는다. 소스 식별 정보를 유지하고 가중치를 변경하지 않는다.
HF 대조군도 변환 모델의 순전파를 공유하므로 상위 프로젝트의 네이티브 구현과 변환본의
동일성을 독립적으로 입증하는 검사는 아니다.

### 다시 열린 EOS 통과 조건

자연 EOS 검증은 미완료이며 후속 성능 작업은 보류 상태다.
[단순 입력 후속 검사](../evidence/english_blt_simple_termination_20261027.json)는
짧은 영어·한국어 문장 네 개를 원문·GEC 형식으로 검사한다. 입력 여덟 개 모두 양쪽
모드에서 새 ID 128개의 진단 상한에 도달했다. 원문 `Hello.`는 단순 반복이 아니라
학생 소개를 생성했고, GEC 구분자는 자주 반복됐다. 모든 상한 도달을 같은 실패나
무한 생성의 증거로 해석하지 않는다. `diagnostic_complete`는 대조 검사 완료만 뜻한다.

중요하게도 현재 기반 가중치의 해시는
`4b6115bd01f6793b4a3afb6734f16b7204e841cb9248e23cd79b67ef01fff061`이며,
과거 A100 네이티브 평가는 학습 가중치를
`cc8466be70e67e7164d14a271818bef42a919914cd7737b6471c1f3b7454ab28`로 식별한다.
원래 평가기는 변환된 기반 모델을 만든 뒤 학습 가중치를 읽지만 현재 기본 동작
검사기는 그러지 않는다. 같은 모델 상태가 아니다. 사용자가 이전에 성공한 검사는
정확한 체크포인트와 명령을 확인해 재현해야 한다. 이 불일치를 정상적인 기반 모델
동작이라며 넘기거나 EOS 통과 조건을 다른 작업으로 대체하지 않는다.

진단 실행기의 `--simple-controls`로 새 출력에 짧은 입력 검사를 반복할 수 있다.
원래 HF 대조군은 원래 생성 함수처럼 `logits_to_keep` 인자를 명시하지 않는다.
그 사실만으로 HF 내부가 전체 로짓을 계산한다고 보장되지는 않는다.
프롬프트에 EOS를 넣거나 강제하지 않으며 반복 페널티로 유도하지도 않는다.

### 실제 EOS 관측

사용자는 이전 성공 검사가 GEC나 A100 학습 체크포인트와 무관한 일반 HF 모델
생성이었다고 명확히 했다. 앞서 구분한 학습·기반 가중치 해시로는 그 검사를 설명할 수
없다. 정확한 모델과 버전은 미확인 상태이며 재현에 GEC 체크포인트를 요구하지 않는다.

공식 Transformers BLT 클래스는 변환 가중치 키 510개를 누락·예상 밖 키·텐서 불일치
없이 받아들였다. 탐욕 생성은 짧은 대조 입력 여덟 개 모두 128 ID에 도달했다.
별도로 원문 `Hello.`에서 seed20261027, `do_sample=True`, `top_k=0`,
`top_p=1`, `temperature=1`을 사용하자 새 ID459로 EOS2를 생성하고 1024-ID 상한
전에 멈췄다. 이 [샘플링 근거](../evidence/english_blt_sampled_eos_20261027.json)는
실제 EOS 관측이지 탐욕 생성 성공이 아니다. EOS 강제나 반복 페널티는 사용하지 않았다.
`Hello.`의 OSC/count 샘플링은 seed20261027과42에서 여전히 1024 ID에 도달했다.
해당 실패도 근거 디렉터리에 남아 있다.

공식 샘플의 EOS 직전 접두부를 재생하자 count 탐욕 생성은 새 ID14로 EOS를 내며
종료했다. 자연 종료한 그 접두부에서 EOS를 빼고 재생하자 원래 OSC와 count 모두
첫 새 ID로 EOS를 골랐다. EOS 확률은 0.63226587과 0.51344788로 둘 다 순위1이었다.
[최종 EOS 근거](../evidence/english_blt_eos_manual_hf_20261027.json)는 변경하지 않은
수동 `greedy_generate` 도우미와 HF도 비교한다. 양쪽 모드 모두 정확히 `[2]`를
반환하고 멈췄으며 입력에는 EOS가 없었다.

이는 현재 두 경로의 실제 EOS 출력과 종료 처리를 검증한 것이지 임의의 짧은 입력에서
시작한 전체 탐욕 생성의 종료를 검증한 것이 아니다. 완료된 접두부는 위 진단 과정을
통해 선택됐으므로 편향 없는 평가 집합이나 처리량 벤치마크가 아니다. 이전의 짧은
프롬프트 탐욕 생성 상한 도달은 미해결 상태다. 이 관측을 얻기 위해 모델 가중치나
실제 사용 경로의 생성 동작을 변경하지 않았다.

진단 옵션 `--official-only`는 라이브러리 구현을 선택하며,
`--sample-eos --sampling-seed N`은 필터 없는 샘플링을 명시적으로 활성화한다.
`--sample-eos` 없이 `--eos-reference PATH --eos-reference-mode count_lmdb`를
사용하면 기록된 자연 EOS 접두부에서 EOS 자체를 제외하고 양쪽 OSC 모드의 탐욕
생성을 재생해 수동·HF 출력 ID를 비교한다.

### 상한을 늘린 일반 입력 진단

실행기는 프롬프트와 생성 길이의 합에 문맥 길이 제한을 적용하면서 명시적인
`--max-new-tokens`를 받는다. 기존 기본값은 그대로다. 이 후속 검사는
`--simple-controls --raw-only --max-new-tokens 2048`을 사용하고 GEC 구분자와
선별한 EOS 문맥은 제외했다. [2048-ID 근거](../evidence/english_blt_eos2048_20261027.json)는
고정된 영어·한국어 입력 네 개를 원래 OSC와 count 모드에서 탐욕 생성·캐시 없음으로
실행한 결과다.

원래 `Hello.`는 새 ID514에서 EOS로 멈췄다. count는 이 입력에서 2048 ID에
도달했고 다른 세 입력은 양쪽 모두 2048에 도달했다. 따라서 EOS 비율은 1/4 대
0/4였다. 출력 여덟 개 모두 유효한 UTF-8이었고 첫128-ID 접두부도 모두 이전의 짧은
입력 진단과 같았다. 상태는 명시적으로 `completed_with_generation_limits`다.
선택한 입력 네 개만으로 일반적인 종료율이나 통계적으로 검증된 패처 퇴행을 입증할
수는 없다.

`Hello.`의 여덟 ID 창 반복 비율은 원래 0.1897, count 0.7511이었다. 다른 입력은
0.9334-0.9863 범위였다. 이 기술 통계는 EOS를 제외한 생성 바이트 ID의 여덟 바이트
창에서 `1 - unique_windows / total_windows`로 계산하며 보정된 품질 점수가 아니다.
단회 경과 시간은 입력별 준비 실행이나 순서 교대가 없고 출력 길이도 다르므로 같은
작업량의 가속 측정이 아니다.

다음 패처 검증은 먼저 미사용 영어 문서와 품질 계약을 고정해야 한다. 같은 정답
텍스트를 강제 입력하면서 바이트 가중 BPB와 문서별 차이를 측정하고, 기준 패처 경계의
정밀도·재현율과 패치 길이 분포도 함께 측정한다. 평가 집합에서 재조정하거나 F1과
F0.5를 혼동하지 않는다. 패치 대체 후 생성 경로가 갈라지므로 출력 동일성은 이
대체 패처의 채택 기준이 아니다. 캐시 재사용의 출력 동일성 계약과도 별개다.
품질 허용치를 합의한 뒤에만 초기·증분 처리의 반복 타이밍과 호스트·GPU 메모리를
채택 근거로 사용한다.

선택하지만 가격 비교를 거꾸로 설명하고 무관한 글을 추가한다. count의 비·빵 설명과
백업 추천은 핵심 종점에 이른 뒤에도 문단이나 빈 줄을 반복한다. 따라서 EOS는 작업
품질을 보장하지 않으며 의미상 완료된 모든 답변을 포착하지도 않는다.

명확한 지시만으로는 이 고정 집합의 상한 도달·반복 문제가 사라지지 않았다.
기반 모델 동작과 패치 대체 모두 출력에 영향을 줄 수 있다. 이 작고 다른 프롬프트
집합은 이전 원문 문장 입력과의 통제된 인과 비교가 아니며 일반적인 모델 품질이나
패처 채택을 입증하지 않는다. 이 실행을 위해 모델이나 임계값을 다시 학습하지 않았다.

### EOS 인과 진단 (2026-10-28)

현재 탐욕 설정은 **실용 생성용으로 승인하지 않는다**. 고정 작업 실행의 16/18이
2048-ID 상한에 도달했고, EOS 출력 두 개도 모두 내용상 결함이 있었다.
상한 확대는 입증된 해결책이 아니다. 이 판단은 검사한 설정에 한정하며 모든 BLT
모델이나 실행 환경에 적용하지 않는다.

[고정 문맥 근거](../evidence/english_blt_eos_causes_20261028.json)
(SHA256 `56855a609d0334c6fd370e3f83ad15eb60c34b42d8696d7c6e35d85ee9c967ad`)에는
점수 측정 320개가 있다. 기록된 전체 18개 경로에서 문맥 80개를 선택해 각각
공식 HF BF16, OSC BF16, count BF16, OSC FP32로 평가했다. 프롬프트만 있는 문맥은
양쪽 원본 경로에 중복되므로 독립 표본이 아니다. 선택 위치는 0/128/512/마지막 기록
선택 지점과 후행 공백 시작점이며, 가능한 경우 공백 시작 뒤 16 ID 지점도 포함한다.
입력에는 EOS가 없다. 자기 경로의 다음 ID 대조군 80개가 모두 원래 기록을 재현했다.
실행기는 [진단 스크립트](../scripts/diagnose_blt_eos_causes.py)다.
itcerdo에서 집중 테스트 9개와 전체 38개가 통과했으며 편집기 진단에도 문제가 없었다.

**측정된 작동 양상: 탐욕 선택과 스스로 강화되는 줄바꿈 꼬리.**
원래 OSC 여행 비교 경로의 아래 점수는 모두 변경하지 않은 같은 모델에서 얻었다.
생성 위치는 다음 선택 전까지 생성한 ID 수다.

| 생성 위치 | EOS 확률 | 줄바꿈 확률 | 탐욕 선택 |
| --- | --- | --- | --- |
| 412, 공백 꼬리 시작 전 | 19.1629% | 75.791% | 줄바꿈 |
| 428, 공백 ID 16개 뒤 | 1.2184% | 85.417% | 줄바꿈 |
| 2047, 마지막 기록 선택 | 0.00069% | 99.955% | 줄바꿈 |

EOS는 내내 허용됐다. 확률이 양수라는 사실만으로 탐욕 생성이 멈추지는 않는다.
백업 OSC 경로도 위치 655의 EOS 7.7738% / 줄바꿈 86.229%에서 위치 2047의
EOS 0.00029% / 줄바꿈 99.958%로 변했다. count 자체의 여행·백업 경로도 같은
방향이었다. 네 구현 모두 긴 공백 경로 네 개의 마지막 위치에서 줄바꿈을 골랐다.
꼬리의 공백 ID 수는 여행(OSC/count) 1636/1360, 백업 1393/939였다.
공백 ID 수는 이전 검토의 빈 줄 수와 다르다. 선택한 위치들은 기록 경로에서 분포가
집중되는 양상을 보일 뿐, 매 단계의 단조 변화나 모든 문장 반복의 원인을 입증하지 않는다.

**다른 원인과 대조 검사:**

- 종료 처리와 토큰 ID: 이전 HF·수동 대조군은 실제 EOS2를 출력하고 멈췄다.
   BOS1/PAD3과 바이트+4 인코딩도 검사했다. 이는 종료 장치가 작동한다는 근거일 뿐
   EOS가 일반적으로 높은 확률을 갖는다는 근거는 아니다.
- count 대체: 자연 EOS 문맥 두 개를 포함한 공통 문맥 80개 모두에서 OSC/count가
   같은 다음 ID를 골랐다. count는 확률을 바꿨고 자유 생성 경로도 다르다.
   이는 count만의 EOS 억제에 반하는 근거이지 전체 출력 동일성이나 패처 채택 근거가 아니다.
- 수치 정밀도: 로드된 같은 BF16 가중치를 FP32로 승격하고 TF32를 비활성화해도
   80/80개 문맥에서 OSC의 다음 선택이 유지됐다. 긴 꼬리의 EOS·줄바꿈 확률도
   비슷했다. 이는 산술 정밀도 진단이지 원래 FP32 가중치 복원이나 전체 FP32 생성이 아니다.
- 공식 구현: 77/80개 문맥에서 다음 선택이 OSC와 같았다. OSC/count가 EOS를 고른
   두 문맥 모두에서 공식 HF는 공백으로 계속했다. 시계 결말의 EOS 확률은 공식
   0.5669%, OSC 76.4063%, count 83.1046%였고, 노트북 결말은 각각
   0.09504%, 66.5348%, 71.8488%였다. 공식 HF는 같은 변환 가중치와 전체 인과적
   어텐션 의미를 사용했다. 구현 차이는 실제지만 공식 HF로 교체하는 것이 입증된
   종료 해결책은 아니다. 점수표만으로 원인이 되는 층을 특정할 수 없다.
- 프롬프트와 디코딩: 명시적인 완료 지시도 이 고정 집합에서는 실패했다. 앞선
   OSC/count 샘플링도 검사한 두 시드에서 모두 1024 상한에 도달했다. 샘플링은
   종점 근처의 탐욕 분기를 피할 수 있지만 고정 집합 전체의 성공과 내용 품질은
   미검증이다. 꼬리 분포가 집중된 뒤 늦게 샘플링하는 것은 원래 프롬프트부터
   샘플링하는 것과 다르다. 이를 단순한 기반 모델 한계로 치부할 근거는 없다.

**과거 변환 검사가 실제로 입증한 범위:**

itcerdo에서 원래 프로젝트의
`blt_hf_checks/results/weights_p1_validation_20260915.json`
(SHA256 `97c8988056486cff1cc9ffc7597ec9d954ee10e56b7f6b769af2d50e4e54fa7d`)은

검사를 통과했다. 변환 보고서 해시는 현재 산출물과 같지만 순전파 동일성은 명시적으로
미검증으로 남겨 둔다. 패치 동일성 검사기는 같은 엔트로피 로짓으로 엔트로피 산술과
스칼라 분할을 비교하며 원래 엔트로피 순전파의 동일성은 검증하지 않는다고 명시한다.
OSC 기본 동작 검사도 유한 손실과 생성을 기록할 뿐 자연 완료를 확인하지 않는다.

따라서 해당 `passed` 상태는 사용성 인증이나 상위 구현과 전체 순전파가 같다는 증명이
아니다. 변환이 실패했다는 주장도 아니다. 사용자가 이전에 성공한 HF 생성은 과거
GEC/A100 평가가 아니라 아직 모델·실행 환경이 확인되지 않은 별도의 실험이다.

**남은 인과 분석의 순서:** 원본 상위 구현과 원본 체크포인트로 같은 접두부의 다음
로짓을 재현하며 엔트로피·패치 경계·어텐션 의미를 포함한다. 이후 같은 예산과 명시적
품질·반복·EOS 기준으로 사전에 정한 프롬프트·시드의 디코딩 비교를 실행한다.
첫 단계는 공통 변환·실행 오류와 학습된 모델 동작을 구분하고, 다음 단계는 디코딩
변경이 단지 EOS를 내는 것을 넘어 실제 쓸 수 있는 답변을 개선하는지 검사한다.
여기서는 이 단계들을 실행하지 않았다. 강제 종료·페널티·가중치 변경·임계값 재조정이나
성능 최적화로 대신하지 않았다.

### HF 단계별·마스크 개입 검사 (2026-10-28)

**범위 수정:** 이후 사용자 지시는 기존 HF 환경을 유지하고 상위 실행 환경 재구축을

명시적 `total` 단계는 매 반복 어댑터 상태를 초기화한 뒤, 최종 길이보다 32 ID 짧은

시작·초기 완료·증분 완료에서 GPU를 동기화한다. 모델 로드·어댑터 reset·준비 실행·

측정한 것이 아니라, 초기 처리부터 포함한 같은 작업량의 접두부 재생 비용이다.

초기 처리 한 번과 확장 순전파 32번으로 실행 블록당 순전파는 33회다.
입력별 준비 세 번·측정 열 번과 모드 교대를 유지했다. 기록은 실행 블록 160개,

### 확률론 패처의 조회·계산·전송 비용 분해 (2026-10-29)

사용자 요청에 따라 초기 처리 병목을 최적화하지 않고 비용만 분해했다.
[원본 표본](../evidence/english_count_patcher_costs_20261029.json)의 SHA256은
`68124f7f559b7a7b8b841c0daffa83b3917d82f414bcf252d99891e576ea1b1f`다.
[계측 스크립트](../scripts/profile_count_patcher.py)는 원래 어댑터·카운트 계산을
그대로 호출한다. 기존 total 보고서의 입력8개·고정 규칙·배경 메타데이터·패키지
소스 해시와 Torch/GPU가 같은지 검사했다. 초기 접두부는224/480/992/2016 ID,
증분은 같은32바이트다. 패처 상태를 반복마다 초기화하고 증분 준비 접두부 처리는
측정에서 제외했다. 준비3회·측정10회, 계측 없는 baseline과 계측 실행 순서를
교대했다. LRU4096행 캐시를 유지하고 저장장치 콜드 상태는 만들지 않았다.

**분모는 전체 BLT 모델이 아니라 확률론 패처 단독의 계측 실행 시간이다.**
모델 가중치는 로드하지 않았다. 기존 전체 모델 측정과 다른 실행이므로 여기의
시간을 이전 모델 시간에서 직접 빼거나 구성비로 적용하지 않는다.

- 조회: 배경 `lookup`과 온라인 카운트 `lookup`의 합. 배경 조회에는 LRU 접근과
   캐시 미스 시 LMDB 읽기·행 해석이 포함된다. 순수 디스크 I/O 시간은 아니다.
- 입출력·전송: 입력 GPU 텐서의 `tolist()`와 결과 `torch.tensor` 생성·GPU 완료.
   Python 목록 변환·할당·호출 비용도 포함하므로 순수 버스 전송 시간은 아니다.
- 계산·기타: 전체에서 위 두 항목을 뺀 나머지. 확률·엔트로피·경계 계산,
   온라인 카운트 갱신·문맥 구성, 검증·할당, Python·계측 오버헤드가 포함된다.
   순수 산술이나 Python 인터프리터만의 비율을 뜻하지 않는다.

비율은 각 항목의 원시 시간 합계/계측 전체 시간 합계다. 중앙값 비율을 더한 값이

확률 계열의TP275426/FP128558/FN63472에서 위 Precision/Recall/F1/F0.5를 계산했다.
엔트로피의100%는 자기 비교 기준값이지 정답 경계에 대한100%정확도가 아니다.
출력 재현은 프롬프트·시드가 같은 쌍의 **생성 ID 전체가 같은지** 보는 별도 지표다.
경계F1 74.1507%를 생성 텍스트 유사도·정답률로 해석하지 않는다.

**바이트·시간의 의미:** 생성 바이트는 `generated_ids` 중4이상인 ID의 수다.
1 ID가1바이트이고 특수 ID는 제외하므로 문자 수나 특수 ID를 포함한 생성 ID 수와
다르다. 자유 생성 총시간에는 첫 프롬프트 처리·이후 생성·샘플링 등이 포함되고,
동일 작업 모델 시간은 모델 로드·샘플링·바이트 선택·출력 디코딩을 제외한다.
같은 생성18회에 대한 prefill/이후 생성 시간 분해는 따로 기록하지 않았으므로
동일 작업 시간 행을 자유 생성 총시간의 구성요소처럼 더하거나 빼지 않는다.
EOS 달성 비율은 기록된 종료 비율이며 생성 완성도·내용 품질 점수를 대신하지 않는다.

**바이트당 속도 계산:** 초기 입력 분모는8개 초기 접두부의 실제 바이트 합계
7416바이트(BOS 등 특수 ID 제외)다. 초기 시간의10반복 평균 합계를 이 값으로
나누어 us/B를 구하고, 역수로 B/s를 구했다. 1us는100만분의1초다.
동일 증분은8입력×32인256바이트로 나눈 ms/B와 그 역수 처리량이다.
이는 같은 바이트의 모델 순전파 비용이며 실제 샘플링을 수행한 생성 속도는 아니다.

그 역수인 B/s다. **초기 처리·샘플링을 포함한 실효 생성 속도**이며, 초기 비용을

전체 모델 초기 처리는 count가 약4.00배 느리고,패처 단독 초기 처리는 약11.01배 느리다.
패처 단독 증분은 count prefix 재사용 덕분에 약31.22배 빠르지만 본체 전체의 생성
속도비가 아니다. 이번 timing은 model_incremental32/model_total32를 측정하지 않았으므로
과거10GB의 전체 모델 초기+증분 표와 합치거나 새로운 전체 모델 생성 speedup을 주장하지 않는다.

**판정:** 20GB는10GB 대비 BPB/경계 재현이 소폭 개선됐지만 신경망 동등 출력이나
초기 속도 기준을 충족하지 못했다. 기존 후보/기본 백엔드를 자동 채택하지 않는다.
원격 원본/설정/코드 hash와 집계 근거는
[20GB 비교 분석](../evidence/english_blt_20gb_analysis_20261104.json)에 기록했다.

### 20GB 전체 모델32바이트 증분 실측 (2026-11-04)

사용자 요청으로 미측정이던 전체 모델 증분을 별도 `en-blt20gb-total-20261104-01`에서
실행했다. 기존20GB timing의 정확한8입력/모델/20GB 빈도·계수/BF16/OSC/eager/batch1/
beam1/no-model-cache를 유지하고 3회 준비/10회 측정의 모드 교대순서를 적용했다.
기존 conda `phdq_blt_hf`에 누락된 `lmdb==2.3.0` 하나만 사용자 승인으로 `--no-deps`
설치했다. Torch/Transformers/NumPy 버전과 기존 source/결과/LMDB는 변경하지 않았다.
가중치/fit/background/기준 timing/replay 코드 hash와 기존3회귀를 검증했다.

한 초기 순전파와 같은 byte 접두부를1개씩 늘리는32회 전체 모델 순전파를 같은
실행에서 측정했다. 모델 로드/adapter reset/샘플링/디코딩/정확성 검사는 시간에서
제외하며 count 조회·CPU·전송·패처·인코더·전역·디코더는 포함한다.
아래 값은 각 입력의10반복 평균을8입력에 걸쳐 합산한 초이며,단일 입력 시간이 아니다.

| 동일 작업 전체 모델 시간 | 신경망 | 20GB Python count | 판정 |
| --- | --- | --- | --- |
| 초기 접두부 처리 | 0.243407 | 0.980305 | count 약4.03배 느림 |
| 이후 동일32바이트 증분 | 7.834343 | 6.120596 | count 약1.28배 빠름,시간 약21.9% 감소 |
| 초기+32바이트 전체 | 8.077750 | 7.100901 | count 약1.14배 빠름,시간 약12.1% 감소 |

8개 입력 모두에서 count 증분 평균이 신경망보다 낮았다. count 재사용과 fresh-prefix의
경계 및 logits는32단계×8입력 모두 정확 일치했고,각 paired 표본의 초기+증분=합계
잔차는0이다. 이는 count 자기 일관성 검사이지 신경망 출력과의 동등성 검사가 아니다.
실제 최대 host RSS는10118696960bytes로48GiB 미만이며 종료 후 디스크 여유142GiB다.

**판정 보완:** 확률 패처의 전체 모델 증분 이점은 이번 고정 입력 실측에서 확인됐다.
초기 처리만 느리다는 이유로 전체 효용을 부정하지 않는다. 다만 자유 샘플링 속도나
다른 모델/GPU/길이의 동일 이점을 보장하지 않으며 기존BPB/출력 차이도 없어지지 않는다.
20GB C++ 재생은 미측정이고 기본 백엔드 채택은 자동 결정하지 않는다.
앞절의 미측정 설명은 원래3단계 보고서 범위이며 이번 후속 측정으로 보완했다.
원본 `total.json` SHA 및 집계는
[20GB 비교 분석](../evidence/english_blt_20gb_analysis_20261104.json)의 `followup_total32`에 기록했다.
